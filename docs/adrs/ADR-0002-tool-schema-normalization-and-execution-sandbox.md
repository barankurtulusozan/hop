# ADR-0002: Tool Schema Normalization & Sandboxed Execution Engine

**Status:** Accepted  
**Date:** 2026-08-03  
**Deciders:** Platform Architecture Team (Phase 2, PLAT-102)  

## Context & Problem Statement

As our AI platform evolves from simple Q&A into agentic systems, LLMs must invoke external tools (search engines, SQL databases, API endpoints, internal tools). 

However, LLM tool integration presents three major architectural risks:
1. **Vendor Schema Incompatibility.** OpenAI formats tools as `type: "function"` with a nested `parameters` dictionary; Anthropic formats tools with an `input_schema` key and `tool_use` response content blocks. Downstream services should not know which provider is serving the request.
2. **Untrusted LLM Output & Schema Injection.** LLMs frequently output malformed JSON, invalid data types, or missing required fields. Executing unvalidated tool arguments can cause database injection, type crashes, or security vulnerabilities.
3. **Cascading Failures from Unhandled Tool Crashes.** If a tool handler raises an exception or hangs infinitely, the task pool can starve or crash the orchestrator.

## Alternatives Considered

1. **Pass-through Vendor Tool Objects (Status Quo).**
   Product code formats OpenAI or Anthropic tool dictionaries directly.
   *Rejected*: Causes extreme vendor lock-in and forces application services to branch on provider type.

2. **LangChain / LlamaIndex Tool Abstractions.**
   *Rejected*: Bundles complex agent loops and opaque runtime wrappers. Difficult to enforce custom Pydantic validation boundaries, per-tool timeouts, and structured JSON logs.

3. **Hexagonal Tool Port & Pydantic Schema Registry (Chosen).**
   - Core domain models (`ToolDefinition`, `ToolCall`, `ToolResult`) contain zero vendor details.
   - `ToolRegistry` inspects Python type hints or Pydantic models to auto-generate OpenAPI/JSON-Schema specifications.
   - `ToolExecutor` provides a sandboxed execution boundary with timeouts (`asyncio.timeout`) and exception trapping (`is_error=True`).
   - `ToolOrchestrator` implements an Agentic Auto-Correction Re-Prompt Loop: if validation fails, it formats a `Role.TOOL` error turn and re-prompts the LLM to self-correct up to `max_tool_retries`.

## Decision

Adopt Hexagonal Tool Normalization & Sandboxed Execution via `src/domain/tools.py`, `src/tools/`, and `src/orchestrator/tool_runner.py`.

### Architectural Boundary Rules
1. **Zero Vendor Imports in Tools Subsystem:** `src/domain/tools.py`, `src/tools/registry.py`, and `src/tools/executor.py` must never import `openai`, `anthropic`, or `httpx`.
2. **Defensive Validation Boundary:** Every tool call arguments dictionary MUST pass Pydantic schema validation (`validate_arguments`) before entering a handler function.
3. **No Unhandled Tool Exceptions:** The `ToolExecutor` traps all runtime exceptions and converts them to `ToolResult(is_error=True, error=...)`.

## Trade-off Matrix

| Criterion | Pass-through Vendor Tools | Framework Abstraction (LangChain) | Hexagonal Tool Sandbox (Chosen) |
|---|---|---|---|
| Vendor Isolation | None | Low (Framework Lock-in) | Complete |
| Argument Validation | Manual / Per-Call | Implicit | Automatic via Pydantic |
| Failure Isolation | Weak | Partial | Absolute (Sandboxed) |
| Self-Correction Capability | Custom per service | Built-in (opaque) | Explicit & Configurable |
| Execution Overheads | ~0ms | 10–50ms framework overhead | ~0.5ms validation overhead |

## Consequences

**Positive:**
- Adding a new tool is as simple as registering a Python function with `@registry.register()`.
- Malformed tool arguments generated by LLMs are caught before function invocation and automatically re-prompted for self-correction.
- Timeout protection prevents hanging tool calls from blocking event loops.

**Negative / Accepted Costs:**
- Complex non-JSON-serializable return values must be serialized to string or JSON-compatible types for LLM context turns.
